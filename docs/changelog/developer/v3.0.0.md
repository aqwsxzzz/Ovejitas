# v3.0.0 Developer Changelog

## Scope

Consumes backend releases `#49`–`#53` (`develop@96f8256` … `develop@1e19bce`) and corrects the
frontend assumptions they invalidated. Three domains are affected: produce/product modelling,
calendar handling, and per-asset profitability. Plus a set of UX dead ends found while probing the
running API.

13 commits, 76 files, +2359 / −852 against `v2.0.0`.

## Architecture / Design Changes

**A product is its production category, and it owns its produce pool.** Previously "Huevos" was two
records the farmer created independently — a `production` event category (for the meta and the
productivity report) and a look-alike `produce` asset (for stock and revenue) — with nothing
keeping them in agreement. `event_category.produce_asset_id` now links them, the backend provisions
the pool when the category is created, and `POST`/`PATCH /assets` reject `kind=produce`. The
frontend consequence is that a harvest names one thing, and the two-picker form collapsed to one.

**Pool↔product mapping is centralised.** `asset.produce_asset_id` still stores a *pool* id while
every picker now speaks in *products*, so `src/features/livestock/utils/product-utils.ts` owns both
directions of that lookup rather than each form re-deriving it.

**Farm-local dates replace browser-local dates.** The backend anchors naive bounds to
`farm.timezone` and rolls a bare `date_to` to the next farm-local midnight. Sending
`Date.prototype.toISOString()` produced an offset-carrying bound that the backend honours literally,
so windows silently followed the browser's calendar. `src/lib/datetime.ts` gained `toDateParam` /
`toDateParamOffsetDays`, and every window sender now emits bare `YYYY-MM-DD`.

**Per-asset profitability reads `profitability-full`, not R1.** R1 books feed cost on the material
that was purchased, never on the consumer, and applies no kind filter. The insight lists therefore
missed real losses and included two structurally-distorted kinds. See the API section.

## API and Data Contract Changes

**Breaking**

- `HarvestCreate` no longer accepts `produce_asset_id`. Pass `category_id` alone; the pool is
  resolved from `event_category.produce_asset_id`. Sending the old field fails the whole request
  (`extra="forbid"`).
- `POST /assets` and `PATCH /assets/{id}` reject `kind=produce` with `422`.
- `AggregateRow.bucket` is a bare calendar date (`"2026-04-10"`), not a date-time.

**Additive**

- `EventCategoryRead` exposes `produce_asset_id: integer | null` and `unit`. The frontend type was
  missing `unit` entirely, despite the backend always returning it.
- `POST /auth/register` accepts an optional IANA `timezone`.
- `production_target.effective_from` accepts any date, including past ones (always did — only the
  form hardcoded today).

**Semantic, same shape**

- `date_from` / `date_to`: a naive bound is farm-local wall clock; an offset-carrying bound is an
  exact instant, honoured literally.
- `production-productivity` widens both window ends to whole farm-local days, and individual-mode
  assets report headcount at all — previously a `per_head_continuous` target on a tagged herd
  returned `expected = 0.00` and `productivity_pct = null` permanently, with nothing flagging it.

**Contract doc corrections**

`docs/backend-event-ledger-rules.md` wrongly described `profitability-full` as single-currency with
a `has_other_currency` flag. It is per `(asset, currency)` and has no such field; that flag exists
only on `produce-outcome`. The frontend types were correct.

## Implementation Notes

**Query parameter name.** `produce-outcome` was being sent `asset_id`; the endpoint parameter is
`producer_asset_id`. The wrong name was silently ignored, so the request returned every producer and
the panel filtered client-side. Now filtered server-side, verified by a bogus id returning zero rows.

**Unit locking derives from the balance, not from configuration.** Movement forms offer only the
units an asset already holds. An asset with no stock keeps every unit open, because its first
movement is what sets the unit — matching `validate_produce_unit` exactly.

**Confirmation split from execution.** `useFlockEventActions` now exposes `requestDeleteEvent`
(opens the dialog) separately from `handleDeleteEvent` (performs the delete), so the confirmation
lives in the UI. `onDeleteEvent` on the timeline is consequently `void`, not `Promise<void>`.

## Code Examples

The unit choice is validated during render rather than stored, because the balance arrives after the
dialog mounts and a stored default would stick at `kg`:

```ts
const options = stockedUnits.length > 0 ? stockedUnits : EVENT_UNITS;
const unit = chosen && options.includes(chosen) ? chosen : options[0]!;
```

Insight rows use the feed-inclusive bottom line, and never add the produce allocation on top of it:

```ts
const incomeOf = (row) =>
  parseDecimal(row.income_total) + parseDecimal(row.allocated_produce_income);
const netOf = (row) => parseDecimal(row.net_incl_materials); // already includes both
```

## Migrations / Operational Steps

1. **Deploy backend `develop@96f8256` or later first.** Harvest returns `422` against anything
   older. This is the only hard ordering constraint.
2. No frontend migration or data change. The backend's own migrations pair existing categories to
   pools and abort rather than guess on ambiguous data.
3. No reseed required. The productivity fixes (`#51`–`#53`) are report-side and retroactive.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Harvest fails on an older backend | Deploy order documented above; breaking change flagged in the commit and both PRs |
| Finance figures move for existing data | Expected: feed cost now reaches the consumer. Called out in release notes so it is not read as a regression |
| Temporary `date_to` patch ships | Isolated in one named helper with the retiring condition documented; no current UI path reaches the case it does not cover |
| Product rename leaves a stale pool name | Backend-owned, raised in `docs/be-request-produce-fifo-ordering.md`; not masked in the frontend |
